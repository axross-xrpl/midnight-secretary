# profile-page-spec.md — プロフィール設定画面（SCR-04a）設計書

対応画面: `basic-spec.md` §5 の **SCR-04a（設定画面.プロフィール設定）**
対応テーブル: `db-design.md` §6.1 `user_profiles`（`db-design.md` §11 の対応表どおり）

本書は画面と、その画面が NeonDB を読み書きする経路を決める。実装コードは書かない（`CLAUDE.md` のドキュメント方針）。

---

## 1. スコープ

### 対象

- 設定画面に **プロフィール設定ページを1枚追加**する（現在は設定ナビの「プロフィール」が灰色の非活性ラベル）。
- `user_profiles` の **1行（サインイン中のユーザ自身）** の参照と保存。
- **支払元のウォレットアドレス**（SCR-04c ができるまでの暫定・§4.6）。
- 本人確認のうち **年齢確認（`age`）と住居確認（`residence`）の述語の元になる属性**を入力できるようにする（`db-design.md` §7.2）。

### 対象外

| 項目 | 理由 |
|---|---|
| 他ユーザのプロフィール参照・管理 | 全画面がサインイン中の1ユーザ分しか扱わない（`db-design.md` §14-9） |
| プロフィールの削除・退会 | 旅程・決済が参照するため、MVP では経路を作らない |
| 本人確認の証明そのものの生成・提示 | Midnight 側の設計（`db-design.md` §14-6） |
| `GET /api/profile` | 画面はサーバコンポーネントから DAL を直接呼ぶため不要（§6.5 に判断を記載） |
| `nationality`（国籍）の入力 | MVP では国籍確認を扱わないため画面項目を持たない。列は残し、本画面の保存では触れない（§6.3・§13-2） |

## 3. 画面レイアウト

サービス管理（SCR-04b）が左リスト＋右詳細の2ペインなのに対し、本画面は**対象が1行しかない**ためリストを持たない。
左にフォーム、右に「この設定が手配にどう効くか」の補足パネルを置く。

```
┌ ヘッダ（ロゴ／ナビ／WalletChip）─────────────────────────────────────┐
├ 設定ナビ ──┬──────────────────────────────────────────────────────┤
│            │ Settings / プロフィール設定                             │
│**プロフィール**│ 説明文                                                │
│ サービス    │ ┌ フォーム（最大 720px）──────┐ ┌ 補足パネル(320px)─┐ │
│ ウォレット   │ │ 1 基本情報                  │ │ 本人確認の充足状況  │ │
│            │ │ 2 本人確認に使う情報          │ │  年齢確認  設定済み │ │
│            │ │ 3 拠点                      │ │  住居確認  未設定   │ │
│            │ │ 4 好み                      │ │ ───────────────  │ │
│            │ │ 5 予算と優先度               │ │ 拠点 東京 / 品川    │ │
│            │ │ 6 ウォレット                 │ │ 上限   80,000      │ │
│            │ │                            │ │ 優先度 時間         │ │
│            │ │ [保存]（下端に固定）          │ │ ウォレット 設定済み  │ │
│            │ └───────────────────────────┘ └──────────────────┘ │
└────────────┴──────────────────────────────────────────────────────┘
```

- 補足パネルは SCR-04b の詳細ペインと同じく **`md:sticky`** で画面内に残す。狭い画面ではフォームの下へ回り込む。
- 保存ボタンはフォーム下端に置き、スクロールしても押せるよう**フォーム内で sticky** にする。
- セクションは見出し＋区切り線のみで、タブやアコーディオンは使わない（項目数が 12 と少ないため）。

## 4. 画面項目定義

記号: 必須=✓ ／ 表示のみ=読み取り専用。ラベルは en を正（`messages/en.json`）とし、ja を併記する。

### 4.1 基本情報

| ラベル(ja / en) | 入力種別 | 必須 | DB列 | 補足 |
|---|---|---|---|---|
| メールアドレス / Email | 表示のみ | ✓ | `email` | サインイン中のセッションの値。**画面からは変更できない**（§6.3） |
| 氏名 / Full name | テキスト | – | `full_name` | 0〜80文字 |
| 住所 / Address | テキスト | – | `address` | 0〜200文字。**表示用**で、移動時間の算出にも述語判定にも使わない旨を補助文に出す（`db-design.md` §6.1・§9） |
| 生年月日 / Date of birth | 日付 | – | `birth_date` | `age`（年齢確認）の述語の元。未入力だと年齢確認の要るサービスが候補から落ちる旨を補助文に出す |

### 4.2 本人確認に使う情報

セクション冒頭に「**ここに入れた値そのものは相手に渡さない。条件を満たすことの証明だけを提示する**」旨の説明を置く
（`db-design.md` §7.2 の設計意図をそのまま画面に出す）。

| ラベル(ja / en) | 入力種別 | 必須 | DB列 | 補足 |
|---|---|---|---|---|
| 居住都道府県 / Prefecture of residence | セレクト | – | `residence_pref` | **47都道府県＋「国外」**の固定値。**自由入力にしない**（`residence` の述語が値の一致で判定されるため、表記揺れがあると判定できない） |

### 4.3 拠点

| ラベル(ja / en) | 入力種別 | 必須 | DB列 | 補足 |
|---|---|---|---|---|
| 拠点都市 / Home city | セレクト | ✓ | `home_city` | 交通検索の `from_city` になる。選択肢は `transport_services` の有効行の `DISTINCT from_city`（§6.2） |
| 起点最寄り / Home departure point | セレクト | – | `home_spot` | 選択肢は選択中の拠点都市に対応する `DISTINCT from_spot`。拠点都市を変えたら選択を捨てる |

**選択肢を DB から出す理由**: 自由入力だと `transport_services` に無い都市が入り、交通が1件も当たらない設定を作れてしまう。
SCR-04b の「手配可能な都市」と同じで、**登録済みのサービスから導出する**（`register-page-spec.md` §9）。

### 4.4 好み

| ラベル(ja / en) | 入力種別 | 必須 | DB列 | 補足 |
|---|---|---|---|---|
| 食事の好み / Dining preferences | 複数選択（チップ） | – | `dining_genres` | 選択肢は `place_services` の `kind='restaurant'` かつ有効行の `DISTINCT genre` |
| 趣味・レジャー / Leisure interests | 複数選択（チップ） | – | `leisure_genres` | 同上（`kind='leisure'`） |

- 選択肢は DB 由来だが、**将来追加されるジャンルを先に入れられるよう自由入力も許す**（各10件・1件40文字まで）。
- 未選択でもよい。その場合はジャンルによる絞り込みをしない（`db-design.md` §10 の `place_services` 取得条件から `genre` が外れるだけ）。

### 4.5 予算と優先度

| ラベル(ja / en) | 入力種別 | 必須 | DB列 | 補足 |
|---|---|---|---|---|
| 1旅程あたりの上限 / Budget per trip | 数値 | – | `budget_jpyc` | 0以上の整数。`filter_feasible` のハード制約になる旨を補助文に出す |
| 優先度 / Priority | ラジオ（3択） | – | `priority` | `time` 時間 / `price` 価格 / `comfort` 快適さ。`select_option` の重みを決める（`db-design.md` §10） |

### 4.6 ウォレット

| ラベル(ja / en) | 入力種別 | 必須 | DB列 | 補足 |
|---|---|---|---|---|
| ウォレットアドレス / Wallet address | テキスト | – | `wallet_address` | 8〜200文字。**形式はネットワークに依存するため検査しない**（`db-design.md` §8 と同じ扱い）。SCR-04c ができるまでの**暫定**で本画面が持つ |

**暫定である理由**: `db-design.md` §11 ではウォレットは SCR-04c の担当だが、その画面が未着手で
**支払元アドレスを登録する経路がどこにも無い**ため。SCR-04c を作るときに、この欄をどちらが持つかを決め直す（§14-4）。

### 4.7 本画面に置かない項目

| 項目 | 置き場所 |
|---|---|
| `nationality` | MVP では入力欄を持たない。列は残し、本画面の保存では触れない（§13-2） |
| `created_at` / `updated_at` | 画面に出さない。`updated_at` は競合検知のために往復させるだけ（§6.4） |
| `user_id` | 画面に出さない。セッションから決まる（§6.1） |

## 6. 読み取り・保存の設計

### 6.1 `user_id` の取得（**前提として先に直す必要がある**）

`user_profiles.user_id` は Google アカウントの `sub` を使う（`db-design.md` §6.1）。
しかし現在の認証オプションは **JWT の `sub` をセッションに載せていない**（セッションに出しているのは
アクセストークン関連のみ）。このままではどの行を読めばよいか決められないため、**本画面の前提として次を直す**。

- NextAuth の `session` コールバックで JWT の `sub` をセッションのユーザ id として渡す。
- Google サインインでは `sub` が Google の subject、dev サインインでは Credentials の `id`（`dev-user`）になる。
  **どちらの経路でも同じ1つの列で扱える**ため、モード別の分岐を増やさない。
- サーバコンポーネント用（`requireSession()` の隣）と Route Handler 用（`hasApiSession()` の隣）に、
  **id を返す関数を1本ずつ足す**。既存の2本は変更しない（他画面が使っているため）。

この変更は `db-design.md` §13 に「未反映」として挙がっていた項目そのもので、本画面で解消する。

### 6.2 読み取り経路

サーバコンポーネント（`/settings/profile`）が DAL を直接呼び、結果をクライアントフォームの初期値に渡す。
`db-design.md` §10 の「内部利用は HTTP を経由せずサーバ関数を直接呼ぶ」に従う。

| 読むもの | 内容 |
|---|---|
| 自分のプロフィール | `user_profiles` を `user_id` で1行。**無ければ未登録状態**（`null`） |
| 拠点都市・起点の選択肢 | `transport_services`（有効行）の `from_city` / `from_spot` の組を重複排除 |
| ジャンルの選択肢 | `place_services`（有効行）の `genre` を `kind` 別に重複排除 |

3本は互いに独立なので `Promise.all` でまとめて読む（SCR-04b のページと同じ形）。
起点の選択肢は都市ごとに引き直さず、**組をすべて取得して画面側で絞る**（追加の通信を作らないため）。

**未登録のときの初期値**

| 項目 | 初期値 |
|---|---|
| メールアドレス | セッションの `email` |
| 氏名 | セッションの `name`（あれば） |
| 拠点都市 | 選択肢が1件ならそれ、複数なら未選択 |
| 食事の好み・趣味 | 空配列 |
| その他 | 空 |

### 6.3 保存経路

`PUT /api/profile`（`db-design.md` §10 の表どおりのパス）。DAL は **1行の upsert** にする。

- 行が無ければ INSERT、あれば UPDATE。画面側に「新規作成」と「更新」の2モードを持たせない。
- `user_id` と `email` は**リクエストボディから受け取らない**。サーバがセッションから決める
  （クライアントが他人の行を書き換えられる経路を作らないため）。
- `email` は **INSERT 時のみ**設定する。UNIQUE 制約があるため更新時に触ると衝突の扱いが増える（§13-3）。
- `wallet_address` は本画面が持つので UPDATE の SET 句に入れる。他の任意項目と同じく、**送らなければ NULL になる**。
- `nationality` は本画面が持たないので、**保存経路が触れない**（値が入っていても消えない）。
- `updated_at` はアプリ層で必ずセットする（`db-design.md` §12。トリガは置かない）。

### 6.4 競合検知

SCR-04b と同じ「取得時の `updated_at` を送り、不一致なら 409」を使う。タブを2枚開いた場合に後勝ちで消えるのを防ぐ。

| 送られた `updatedAt` | 行の状態 | 結果 |
|---|---|---|
| 無し | 行が無い | INSERT する |
| 無し | 行がある | **409**（別経路で作成済み。再読み込みを促す） |
| 有り | 一致する | UPDATE する |
| 有り | 不一致 | **409** |
| 有り | 行が無い | **404** |

### 6.5 API

| メソッド | パス | 用途 | 応答 |
|---|---|---|---|
| `PUT` | `/api/profile` | 自分のプロフィールの保存（upsert） | 200: 保存後の行 ／ 401 ／ 422（検証・制約違反）／ 404 ／ 409 ／ 500 |

- 認証必須。未サインインは 401（既存の応答ヘルパを流用）。
- 検証エラーはフィールド名をキーにした形で返す（SCR-04b と同じ。画面は各欄の下に赤字で出す）。
- **`GET /api/profile` は作らない**。画面はサーバコンポーネントで読むため利用者がいない。
  `db-design.md` §10 の表には `GET` も載っているので、同表に「画面はサーバ関数を直接呼ぶため未実装」と注記する。

## 7. バリデーション仕様

クライアントとサーバの両方で行う（画面は即時性、サーバは正しさ）。DB の CHECK 制約と対応させる。

| 項目 | 規則 | DB側の裏づけ |
|---|---|---|
| 氏名 | 0〜80文字 | – |
| 住所 | 0〜200文字 | – |
| 生年月日 | `YYYY-MM-DD`・未来日不可・1900-01-01 以降 | `date` 型 |
| 居住都道府県 | 47都道府県＋「国外」の固定値のいずれか | – |
| 拠点都市 | **必須**・1〜80文字 | `home_city` NOT NULL |
| 起点最寄り | 0〜120文字 | – |
| 食事の好み / 趣味 | 各10件まで・1件40文字まで・重複不可 | `text[]` NOT NULL（既定 `{}`） |
| 1旅程あたりの上限 | 0以上の整数 | `budget_jpyc >= 0` |
| 優先度 | `time` / `price` / `comfort` のいずれか | `priority` の CHECK |

- 空文字は `null` として保存する（SCR-04b の任意テキストと同じ前処理）。
- エラーはフィールド直下に赤字で表示し、保存時は最初のエラー項目へスクロールする。
- **DB の CHECK と画面の規則を一致させる**。将来 `priority` を増やすときは、CHECK・固定値・画面の3か所を同時に変える
  （`db-design.md` §14-3 と同じ運用）。

## 8. 状態設計

| 状態 | 表示 |
|---|---|
| 未登録（行が無い） | 空のフォーム＋「まだ保存されていません。拠点都市を選んで保存してください」 |
| 読み込み | サーバコンポーネントで取得するため**ローディング状態を画面に持たない**（初回表示の時点で値が揃う） |
| 保存中 | 保存ボタンをスピナー付きで無効化。入力欄は触れる |
| 保存成功 | トースト「保存しました」。フォームを保存済みの値で更新し、新しい `updatedAt` を保持する |
| 検証エラー(422) | 各欄の下に赤字。入力内容は保持する |
| 競合(409) | 画面上部にバナー「別の場所で更新されています。再読み込みしてください」＋［再読み込み］ |
| 通信エラー(500/ネットワーク) | 画面上部にバナー「保存できませんでした」＋［再試行］。入力内容は保持する |
| 未保存のまま離脱 | 確認ダイアログ「保存されていない変更があります」 |
| DB 接続不可 | サーバコンポーネントの取得が失敗したら、フォームの代わりにエラー面と［再読み込み］を出す |

## 11. 実装の順序

1. **セッションからユーザ id を取れるようにする**（§6.1）。ここが決まらないと以降が書けない。
2. 固定値と入力検証スキーマ。
3. 読み取り DAL（プロフィール1行・拠点の選択肢・ジャンルの選択肢）。
4. 書き込み DAL（upsert・競合検知）と `PUT /api/profile`。
5. 設定ナビの現在ページ判定を直し、「プロフィール」をリンクにする。
6. 画面（サーバのページ＋クライアントのフォーム＋右の充足状況パネル）。
7. i18n（en → ja）。
8. 検証（§12）とドキュメント反映（§10 の「変更」）。

1〜4 だけで「保存できる」ところまでは動くため、**5〜6 の前に API 単体で確認できる**。

## 12. 受け入れ条件

1. 設定ナビの「プロフィール」から SCR-04a を開ける。現在ページのハイライトがプロフィール側に移る。
2. 未登録の状態で開くと空のフォームが出て、メールアドレスにサインイン中のアドレスが表示される。
3. 拠点都市を選ばずに保存すると、その欄の下にエラーが出て保存されない。
4. 保存すると `user_profiles` に1行できる（`user_id` はサインイン中のユーザ、`email` はセッションの値）。
5. 再読み込みすると保存した値が復元される。
6. もう一度保存すると同じ行が更新され、`updated_at` が進む。行は増えない。
7. 生年月日と居住都道府県を入れると、右パネルの2つの確認がどちらも「設定済み」になる。
8. 優先度に `time` / `price` / `comfort` 以外は送れない（画面はラジオ、サーバは 422）。
9. ウォレットアドレスを保存して再読み込みすると復元される。8文字未満は 422 で拒否される。
10. 別タブで保存した後に古い画面から保存すると 409 になり、再読み込みの案内が出る。
11. `npm run lint` / `npm run typecheck` / `npm test` / `npm run build` が通る。

**テストの範囲**: 入力検証スキーマと充足状況の判定は純粋関数なので vitest で確認できる。
DAL は `server-only` を読み込むため `npm test` から直接は読めない（既存のカタログ読み取りと同じ制約）。
DAL と API は実DBに対する手動確認で担保する。

## 15. プロフィールが手配に効く経路

保存したプロフィールは、会話画面の提案 (`POST /api/proposals`) で使う。
サインインしていないときはプロフィールが無い状態として扱い、その旨を AI に伝える。

**現バージョンの方針**: 候補を消す処理（ハード制約）は使わず、**本人確認を満たせるかの判断も含めて
すべて AI に委ねる**。除外の判定と経路はコードに残し、`FILTER_BY_VERIFICATION` で無効にしてある（§15.3）。

### 15.1 効かせ方

候補は1件も減らさない。AI に渡す情報と指示だけを変える。

| 項目 | 効かせ方 |
|---|---|
| `birth_date` | **満年齢に変換して**渡す。AI が候補の `ageLimit` と比べて選ぶかどうかを決める |
| `residence_pref` | そのまま渡す。`residence` を要求する候補の判断に使わせる |
| `nationality` | そのまま渡す。`nationality` を要求する候補の判断に使わせる |
| `dining_genres` / `leisure_genres` | 一致するジャンルの候補を**前に出す**（絞り込まない）＋ 好みとして渡す |
| `budget_jpyc` | 選んだ宿泊・飲食・レジャーの合計が上限を超えないよう指示する |
| `priority` | 選ぶ観点（時間 / 価格 / 快適さ）として渡す |
| `home_city` / `home_spot` | 参考情報として渡す。**交通の検索には使われない**（§15.4） |

AI への指示は「満たせない候補、および判断に使う属性が `null` の候補は選ばない。やむを得ず選ぶ場合は、
確認が必要で利用できない可能性があることを理由に明記する」。

**生年月日そのものは渡さない**。候補の `ageLimit` と比較できればよいので、満年齢だけを渡して
外部に出す情報を減らしている。それでも属性値が LLM に渡ることに変わりはなく、
「値を開示せず述語の証明だけを提示する」（`db-design.md` §7.2）という前提とは食い違う。
証明の仕組みが入るまでの割り切り。

### 15.2 保証されないこと

判断を AI に委ねた結果、**本人確認を満たせない候補が提案に出ることを防げない**。

| | 現バージョン | 除外を有効にした場合 |
|---|---|---|
| 満たせない候補が出るか | 出る可能性がある | 出ない |
| AI が落ちた・応答を照合できない場合 | フォールバックは最安値を選ぶだけなので、制約は効かない | 効く |
| 検証 | 実行するまで分からない | 純粋関数として vitest で確認できる |

実際の挙動（16歳・「夜に楽しめるレジャーと、お酒が飲めるお店」で確認）では、AI は 18歳以上の公演とバーを選ばず、
宿泊の理由に「年齢や国籍の制限がなく、利用者の属性で確実に宿泊できる」と書いた。
ただしこれは1回の結果で、**同じ入力で同じ判断になる保証は無い**。

### 15.3 除外を有効に戻す

`src/app/api/proposals/route.ts` の `FILTER_BY_VERIFICATION` を `true` にする。
次のものはそのまま残してある。

- `filterFeasible` / `canSatisfy` / `ageOn`（`src/features/profile/feasibility.ts`・vitest で検証済み）
- 除外した件数と理由を利用者に伝える経路（応答の `notice` と会話画面の表示）
- 候補が 0 件になったときの案内文の出し分け

有効にすると、プロフィール未登録・未サインインでは本人確認を要求する候補がすべて落ちる。

### 15.4 効かない項目

- `home_city` / `home_spot` は交通の検索条件（`from_city`）になる想定だが、
  **交通を検索する画面が無い**ため、現時点では AI に渡す参考情報にとどまる。
  `FareCatalogPort` を使う手配の経路ができたときに接続する。
- `budget_jpyc` は `db-design.md` §10 ではハード制約だが、画面の「上限価格」は**1泊あたり**、
  プロフィールの上限は**1旅程あたり**で単位が違う。単位を揃える設計が決まるまで、
  SQL の絞り込みには使わず AI への指示にとどめる。
- `nationality` は入力欄が無いため常に未設定になる（§13-3）。
